Run: `run-20261013T1320Z` (start 2026-10-13T13:21:53Z). Observations made 2026-10-13 between about 13:22Z and 13:31Z in the user's Chrome (Claude in Chrome, own tab group).

Queries used for schema discovery: `Loteprednol` (name), `0574-4135-05` (NDC), `OZEMPIC` (name, hash-verified capture), `00002250680`, `00002-2506-80`, `00169418113`, `00169-4181-13`, `00310654004`, `00310-6540-04`, `00574413505`, `99999999999` (no-result control), `insulin`, `sodium`, `VICTOZA 2-PAK`.

## 1. Observed facts

### Search mechanics
- Page: `https://ndclist.com/pricing-lookup`. The pricing search box is `input#txtNDCPricingSearch`, button `button#cmdNDCPricingSearch`. There is no `<form>`; the page's inline script handles the click by setting `window.location = "https://ndclist.com/pricing-lookup?sNDCPricing=" + encodeURIComponent(value)`. Enter in the box triggers the same click.
- So a search is a plain GET: `https://ndclist.com/pricing-lookup?sNDCPricing=<encodeURIComponent(query)>`. Navigating to that URL directly produced the same results page as typing and clicking. The URL is stable and was re-used across queries (for example `OZEMPIC` loaded twice with the same 8 rows).
- Results are fully server-rendered into one HTML table; DataTables then paginates client side (`serverSide: false`). The page's DataTables config (read from inline script):
  `order [[1,"asc"]]`, `info: false`, `lengthMenu [[100,200,400,-1],[100,200,400,"All"]]`, `pagingType "full_numbers"`, `searching: true`, `rowGroup {dataSrc: 2}`, `columnDefs [{targets:[2], visible:false}]`.
- The page also has an unrelated header search box (`#txtSearch`, "NDC Lookup"); it is not used.

### "Search results for" text
- `<p class="text-info gi-1-5x">Search results for <em>TERM</em></p>`.
- The echoed term is case-transformed by the site for name queries: `OZEMPIC` -> `Ozempic`, `insulin` -> `Insulin`, `VICTOZA 2-PAK` -> `Victoza 2-pak`. `Loteprednol` and NDC strings were echoed unchanged.
- The page `<title>` keeps the query exactly as sent: `NDC Pricing Search Results for OZEMPIC | National Drug Codes List`.

### Result table
- Table id `table-ndc-pricing-search-results`. Visible header row, exact texts in order:
  1. `` (empty; control column)
  2. `NDC`
  3. `NDC Package Description`
  4. `Price per Unit`
  5. `Pricing Unit`
  6. `Effective Date`
  7. `Labeler`
  8. `Status`
- DataTables holds 9 columns; column index 2 is a hidden column titled `Name`, whose value is the group heading text (for example `0169-4181 - Ozempic`). It is not displayed as a column; it is displayed only as the group heading row.
- Group headings: `<tr class="dtrg-group dtrg-start dtrg-level-0"><td colspan="8">0574-4080 - Loteprednol Etabonate</td></tr>`, format `<product NDC> - <name>`. They are generated by the DataTables RowGroup extension and are not data rows (they are not in `dt.rows()`).
- Package rows: `<tr class="odd">` / `<tr class="even">` with exactly 8 `<td>` cells. Distinguish by class: data rows lack `dtrg-group`. In every query checked, `dt.rows().count()` equalled the number of non-`dtrg-group` `<tr>` in tbody after setting page length to All.
- Control column (cell 0): an `<a class="product_icon" data-toggle="popover" data-trigger="focus">` icon. It is a Bootstrap popover, not a DataTables child row. Its `data-original-title` is a category (observed: `Human Prescription Drug`) and its `data-content` is a drug-use description. Some rows have no icon (OZEMPIC rows 0169-4132-12 and 0169-4136-02). No DataTables child rows exist (`child.isShown()` false for all rows checked). These popover values are captured separately as supplementary details, not as result columns.
- Cell contents: NDC is a link (`<a class="text-bold">0574-4080-05</a>`); Labeler is a link; Status is `<span class="text-success font-bold">ACTIVE</span>` or similar; other cells are plain text.
- What a row represents: one package NDC (10-digit, hyphenated as displayed, e.g. `0169-4181-13`) with one price record. Within each query checked, every NDC appeared exactly once (Loteprednol: 47 rows, 47 distinct NDCs; OZEMPIC: 8 rows, 8 distinct). No historical price series was shown in the result table.
- Field formats observed: Price per Unit `$` + digits + `.` + 5 decimals (e.g. `$10.47371`, `$331.99085`, `$639.13796`). Pricing Unit values seen: `ML`, `GM`, `EA`. Effective Date `MM-DD-YYYY` (all 47 Loteprednol rows matched `^\d\d-\d\d-\d{4}$`; dates seen include `09-23-2026`, `01-01-2025`, `01-06-2022`, `04-23-2025`). Status values seen: `ACTIVE`, `INACTIVATED`, and empty.
- Whitespace detail: the source HTML of NDC Package Description contains a double space before ` / ` (for example `(0574-4135-05)  / 5 mL ...`). The browser renders it as one space (`innerText`). The extractor records both: `ndc_package_description` = source `textContent` (trimmed at the ends only) and `ndc_package_description_rendered` = `innerText`.

### Paging and completeness
- Length control: `Show [100|200|400|All] entries`. Default page length 100. Paging buttons: `First Previous 1 Next Last`.
- No "Showing X to Y of Z entries" indicator: DataTables `info` is disabled in config and no `.dataTables_info` element exists. Completeness is therefore checked through the DataTables API: `dt.page.len(-1)` ("All"), `dt.page.info()` (`pages`, `recordsTotal`, `recordsDisplay`), `dt.rows().count()`, and the DOM row count.
- There is a DataTables filter box (`searching: true`). The extractor asserts the global and per-column filters are empty.
- Broad terms returned large result sets without any visible limit notice: `insulin` 363 rows, `sodium` 309 rows. No round-number cap was observed, but see Unresolved.

### Name vs NDC searches
- `Loteprednol`, `OZEMPIC` (names), and `0574-4135-05`, `00002250680` etc. (NDCs) all produced the same table, same 8 visible headers, same hidden `Name` column.
- An NDC query returns rows at product level when the product has several packages: `0574-4135-05` and `00574413505` each returned 3 rows: `0574-4135-05`, `0574-4135-10`, `0574-4135-15` (same group `0574-4135 - Loteprednol Etabonate`). So NDC-query rows are not guaranteed to be exact matches; the log must mark which returned NDC equals the queried one.

### No-result page
- `99999999999`: no table element; page shows `Search results for 99999999999` followed by `No results found`. `VICTOZA 2-PAK` also returned no table (only the table absence was checked; the "No results found" text was not checked for that query yet).

## 2. Differences from the researched schema in the spec
1. Confirmed as researched: the 7 visible data columns and their order and exact headings; the unlabeled control column before NDC; group headings of the form `<product NDC> - <name>`; 100/200/400/All and First/Previous/Next/Last; sibling packages returned for `0574-4135-05`; status values ACTIVE / INACTIVATED / blank; `MM-DD-YYYY` dates; example row `0574-4135-05 ... $10.47371,ML,09-23-2026,Padagis US LLC,ACTIVE` reproduced (except the whitespace point below).
2. Hidden 9th DataTables column `Name` (index 2) exists and feeds the group headings. The spec did not mention it.
3. The "expanded row" is a Bootstrap popover on the control icon (`data-original-title` category + `data-content` description), not an expandable DataTables child row. Some rows have no icon.
4. "Search results for" echoes the term with the site's own capitalisation for name queries (`Ozempic` for `OZEMPIC`). An exact-string check would wrongly fail; the check must be case-insensitive, backed by an exact check on the URL parameter and the page title.
5. No "Showing X to Y of Z entries" indicator exists (DataTables `info:false`). Completeness has to come from the DataTables API.
6. The description source text has a double space before ` / `; the spec example shows a single space (the rendered form). Both forms are recorded; which one goes into the final CSV is an open decision (below).
7. Search is a URL GET parameter `sNDCPricing`, not a form post.

## 3. Assumptions (not verified)
- The server returns every match in the HTML, with no hidden server-side cap, because 363 and 309 rows came back for broad terms with no limit notice. A cap above those numbers, or a cap that does not show as a round number, cannot be ruled out from the page.
- Each row is the current or latest NADAC record for that package as chosen by the site; the page does not say how the site picks which record to show.
- The popover category and description belong to the drug in the group, not to the specific package.

## 4. Unresolved questions (for the orchestrator)
1. Final CSV description text: source `textContent` (double space, as delivered by the site) or rendered `innerText` (single space, as a viewer sees it)? Both are in the evidence. My suggestion is the source text, with the rendered variant kept in evidence, but that is your call.
2. NDC query form for Pass 1: raw 11-digit and 5-4-2 hyphenated gave identical results on all three tested values.
3. Name-search matching rules are not documented on the page (substring vs word vs product name). `VICTOZA 2-PAK` returned no table in a preliminary check; Pass 2 will record the exact no-result evidence.
4. Whether the effective date shown is the newest NADAC record. The site shows one record per package, so the "newest record" rule in Phase 4 probably only matters if the same NDC comes back with different values from different queries.

## 5. Extraction and integrity mechanism (tested)
- Tool limits found: `javascript_tool` output is cut at exactly 1000 characters (`[TRUNCATED]`), and output that resembles URL query strings or cookies is replaced with `[BLOCKED: Cookie/query string data]`. The extractor therefore never returns URLs with query strings (it records `url_path` and the decoded `sNDCPricing` value separately).
- `scripts/extract.js` runs on the results page. It checks the URL parameter (exact), page title (exact), "Search results for" (case-insensitive, with an exact flag also recorded), empty filters, sets page length to All, confirms 1 page, and cross-checks `dt.rows().count()` = non-group DOM rows = `recordsTotal`; confirms the DataTables node order matches the DOM; confirms 8 cells per row and no open child rows; confirms the NDC cell text equals the DataTables data. It then builds one canonical JSON string (non-ASCII escaped to `\uXXXX` so characters = bytes), computes SHA-256 with `crypto.subtle.digest`, splits it into 900-character chunks with a per-chunk SHA-256 prefix, keeps it in `window.__ex`, and returns `META status rows len chunks sha256`.
- `scripts/chunk.js` returns `k/N <chunk sha16> <chunk>` (under the 1000-char cap).
- The META line and chunk lines are written to `checkpoints/.../capture_<query>.txt` exactly as returned; `scripts/verify_capture.py` checks every chunk hash, the total length, the full SHA-256, JSON parse, and row count, then writes the verified bytes as evidence. A query is marked complete only on PASS.
- Proven on `OZEMPIC`: 8 rows, 5657 chars, 7 chunks, full SHA-256 matched (`dd1715a8...8d45`). Negative control: changing one digit of one price (`$331.99085` -> `$331.99086`) in a copy made the verifier fail with `chunk 4 hash mismatch; full sha256 mismatch`.

## 5a. Decisions from the orchestrator (2026-10-13, after Phase 1)
- **NDC query form:** Pass 1 searches the raw 11-digit input value exactly as it appears in the CSV (for example `00002250680`). There is no hyphenation or conversion. The query string as sent is recorded in every capture (`expected_query`, `url_param_sNDCPricing`).
- **Description text in the final CSV:** use the displayed (rendered, `innerText`) text, which has a single space before ` / `. The source text (`textContent`, double space) is kept in every raw capture as `ndc_package_description` and in `checkpoints/pass1/rows.csv` as `ndc_package_description_source`, so the difference can be traced.
- **Hidden `Name` column:** it is not displayed, so it stays out of `pricing_results.csv`. It is captured per row as `name_hidden_column`, and the displayed group heading row above each package row is captured as `group_heading_displayed`. Both are group context for the lookup log.
- **Match flag for NDC queries:** pad the displayed hyphenated NDC segment by segment to 5-4-2 (`zfill(5)`, `zfill(4)`, `zfill(2)`), join the 11 digits, and compare with the input. The displayed segment lengths are recorded. A displayed NDC that is not three hyphenated numeric segments totalling 10 digits is flagged rather than forced. In Pass 1, every displayed NDC was `4-4-2`, so none was flagged.

## 5b. Extraction mechanism as used in Pass 1
- The extractor in `scripts/extract.js` was converted (comments stripped, the query passed as a parameter, `extractor_sha256` field added) into the function source `scripts/extract_fn.js`, whose SHA-256 is stored in `scripts/extract_fn.sha256` (`8a815c6a...e17a`). That source was stored once in the tab's `sessionStorage` (key `__ext`, scoped to that tab and origin). Each query evaluates it and passes in the SHA-256 of the stored source. The recorder rejects any capture whose `extractor_sha256` differs from the file on disk. The key was removed and the tab closed when the pass ended. N001 used the inline `extract.js` payload, which has no `extractor_sha256` field; the recorder allows that one case explicitly.
- The schema-version-2 capture adds `name_hidden_column` and `group_heading_displayed` per row. The phase-1 field `group_heading` was renamed.

## 5c. Pass 2 (name queries)

The same extractor (same SHA-256), checks, three-way classification and per-query checkpointing as Pass 1 were used (`scripts/record_name.py` is generated from `record_ndc.py` by literal substitutions).
- Name-query rows are recorded with the site's displayed group heading only. They are not labelled as matches for the input drug (`matches_input_ndc` = `n/a (name query)`).

## 5d. Phase 4 dedupe and output rules (as applied)
- Every value in the deliverables is read by `scripts/build_deliverables.py` from the hash-verified evidence files. Each evidence file's SHA-256 is re-checked against `query_attempts.csv` before use. Nothing was typed by hand.
- **Dedup key:** the displayed package NDC text exactly as shown (hyphenated, including both 4-4-2 and 5-3-2 forms), kept as text. Displayed forms are not converted or padded for the key.
- **Identical rows:** rows identical in all seven output fields collapse to one.
- **Newest-date rule:** if an NDC's rows differ, the rows with the newest Effective Date are kept, but only if all rows at that date are identical. Otherwise every competing record goes to `conflicts.csv` with its provenance, no winner is picked, and `pricing_results.csv` is not written. In this run no NDC had differing rows, so neither the newest-date rule nor the conflict path was triggered. `conflicts.csv` is header-only.
- **`pricing_results.csv`:** header `ndc,NDC Package Description,Price per Unit,Pricing Unit,Effective Date,Labeler,Status`. Values are as displayed: price string with `$` and all 5 decimals, `MM-DD-YYYY` date, rendered description, blank status left blank. Standard CSV quoting, `\n` line endings, sorted by ndc.
- **Input coverage:** an input NDC counts as present in the final results when its 11-digit value equals the segment-wise 5-4-2 zero-padded form of a final ndc. That form is used only for this comparison, never for the key.
